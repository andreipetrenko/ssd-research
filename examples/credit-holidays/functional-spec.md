- Кредитная система: чтение текущей просрочки, существующий метод `GET /loans/{id}/delinquency`.

## 3. Функциональное поведение
### 3.1. Проверка права
Сервис запрашивает просрочку по кредиту; при просрочке более 30 дней возвращает отказ `DELINQUENCY_OVER_30`.
### 3.2. Одна активная заявка
Если по кредиту есть заявка в статусе `PENDING`, новая не создаётся; возвращается существующая.

## 4. API и контракты
- `POST /api/v1/loans/{loanId}/holiday-requests` — тело `{ "months": 1 | 3 | 6 }`.
- Ответ 201: `{ "id", "status": "PENDING", "months" }`; 200 — существующая активная заявка.
- Ошибки: 422 `DELINQUENCY_OVER_30`, 422 `INVALID_MONTHS`, 404 `LOAN_NOT_FOUND`.
- `GET /api/v1/loans/{loanId}/holiday-requests/active` — статус активной заявки.

## 5. Данные и миграции
Таблица `holiday_request(id, loan_id, months, status, created_at)`; уникальный частичный индекс
по `loan_id` для статуса `PENDING`. Миграция только добавляет объекты, обратная совместимость сохраняется.

## 6. Безопасность и нефункциональные требования
- Доступ только к своим кредитам: проверка владельца по токену клиента в mobile-bff.
- В логах не сохраняются ФИО и номер договора; используется `loanId`.
- p95 времени ответа — не более 500 мс.

## 7. Тестирование
